#### 重复领取优惠券、重复提交订单等问题
- 问题产生的背景:
  - 1. 用户按钮多次点击
  - 2. 网关层超时重试
- 问题本质:
  - 保证接口`幂等性`
- 解决问题方案:
  - 设置MySql的唯一约束: 用户id + 活动优惠券id
  - `redis`做短期限流和防重: setNX(用户id + 活动优惠券id) + 过期时间；避免短时间并发重复提交
  - MQ削峰
  - 库存扣减: 使用悲观锁 set count -1 where count > 0
  - 悲观锁导致并发量降低: 库存拆分多条记录，提升并发量
  - 发券和库存扣减的一致性: TCC事务

#### 01-MySql唯一索引
  - 比如用户id+活动优惠券id建立联合`唯一索引`
  - 缺点: 唯一索引不能利用`Change Buffer`

#### 02-MySql去重表: 
  - 比如支付单表正常逻辑是订单号唯一，但是如果一个订单可以对应多个支付单，这个时候就没有办法给支付单创建订单号唯一索引，所以需要额外引入以订单号为唯一索引的表

#### 03-Redis Sequence Number
  - 第一步: 先用redis Incr生成sequenceNo(1)
  - 第二步: 再用redis set item:{1}: init记录初始化状态
  - 第三步: 前端提交携带sequenceNo(1)
  - 第四步: 后端校验sequenceNo(1)是否为初始化状态
  - 第五步: 修改状态为process
  - 第六步: 执行业务逻辑
  - 第七步: 修改状态为success
  - 如果服务宕机，业务还没来得及处理，怎么解决？process状态设置过期时间ttl，保证用户可以重试
  - 如果服务宕机，业务已经处理成功，但redis的状态没来得及更新，怎么解决？先查询db，如果数据库已经存在，则回补redis数据。
  - 业务执行失败，怎么解决? process状态设置fail状态

#### 04-Redis Token
  - 先生成唯一token写入Redis，并设置过期时间。提交接口必须携带 token，服务端通过 Lua 脚本原子校验并删除 token，保证 token 只能被消费一次。
  - 更严谨的设计不是简单删除，而是维护 INIT、PROCESSING、SUCCESS、FAILED 状态，成功后记录业务结果，重复请求直接返回第一次结果。

#### 05-状态机: 
  - 订单表的状态(待支付->已支付->已发货->已完成->已取消)

### 分布式事务的最终一致性的解决方案

#### TCC事务(Try-Confirm-Cancel): 预留资源(冻结) + 正式提交
  - 空回滚(Empty Rollback)
  - 悬挂(Hanging): 

#### 空回滚
  - 阻止没有Try的Cancel。
  - 在执行Cancel前，必须检查对应Try的事务日志，确保Try阶段已经成功执行。

#### 幂等
  - 所有阶段操作都能安全重试。
  - 为所有阶段设计状态机，利用事务状态来防止重复执行

#### 悬挂
  - 拒绝迟到的Try请求。
  - Try执行前，检查事务是否已取消；如果已经取消，则直接拒绝；避免资源被错误预留。
