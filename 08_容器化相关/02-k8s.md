## 01-Master Node: KuberNetes的主节点

### 01-01-API Server: Kubernetes控制面板中唯一带有用户可访问API以及用户可交互得组件。
  - API服务器会暴露一个RESTful的Kubernetes API并使用JSON格式的清单文件。
  - 提供集群管理的REST API接口，包括：认证Authentication、授权Authorization、准入Admission(Mutaling & Valiating)。
  - 提供其他模块之间的数据交互和通信的枢纽(其他模块通过APIServer查询或修改数据，只有APIServer才直接操作Etcd)。
  - APIServer提供Etcd数据缓存及减少集群对Etcd的访问。
  - APIHandler -> AuthN -> Rate Limit -> Auditing -> AuthZ -> Aggregator -> Mutating Webhook -> Schema Validation -> Validation Webhook ->

### 01-02-Etcd: 一个强大的、稳定的、高可用的键值存储，被Kubernetes用于长久存储所有的API对象。
  - Etcd是CoreOS基于Raft开发的分布式key-value存储，可用于服务发现、共享配置以及一致性保障(如数据库选主、分布式锁等)。
  - 监听机制；
  - Key的过期及续约机制，用于监控和服务发现；
  - 原子CAS和CAD，用于分布式锁和leader选举。

### 01-03-Scheduler: 调度器会监控新建的pods(一组或一个容器)并将其分配给节点。
  - 特殊的Controller，工作原理与其他控制器无差别。
  - Scheduler的特殊职责在于监控当前集群所有未调度的Pod，并且获取当前集群所有节点的健康状况和资源使用情况，为待调度Pod选择最佳计算节点，完成调度。
  - 调度阶段分为:
    - Predict: 过滤不能满足业务需求的节点，如资源不足、端口冲突等。
    - Priority: 按既定要素将满足调度需求的节点评分，选择最佳节点。
    - Bind: 将计算节点与Pod绑定，完全调度。

### 01-04-Controller Manager: 每个Controller都不断做收敛循环(reconciliation loop)的自动修复。

#### 01-04-01-Deployment Controller: 负责版本发布
  - 实际不直接管理Pod, 而是管ReplicaSet。每次img变换会创建新的RS,旧RS缩到0但保留,用于回滚。
  - 不直接创建Pod，它负责创建ReplicaSet、滚动升级、版本回滚、管理多个ReplicaSet。
  - 策略:
    - RollingUpdate(默认): 逐步替换，零停机；适用于大多数场景
    - Recreate: 先全部杀掉旧Pod，再创建新Pod，存在停机时间窗口；适用于不兼容多版本共存(如DB Schema变更)

## 02-Worker Node: Kubernetes的工作节点

### 02-01-Kubelet: 负责调度到对应节点的Pod的生命周期管理，执行任务并将Pod状态报告给主节点的渠道，通过容器运行时(拉取镜像、启动和停止容器等)来运行这些容器。它还会定期执行被请求的容器的健康探测程序。
  - Kubernetes的初始化系统(init system)
  - 从不同源获取Pod清单，并按需求启停Pod的核心组件:
    - Pod清单可从本地文件目录，给定的HTTPServer或Kube-APIServer等源头获取。
    - Kubelet将运行时，网络和存储抽象成了CRI、CNI、CSI。
  - 负责汇报当前节点的资源信息和健康状态。
  - 负责Pod的健康检查和状态汇报:
    - livenessProbe: 检查容器是否崩溃，失败会重启Pod。
    - readinessProbe: 检查应用是否准备好接收流量，失败会从Service摘除Pod。
    - startupProbe: 保护慢启动容器，在启动成功前禁用其他探针。
    - 探测方法-`HTTP GET`: 检查指定路径的HTTP状态码(如/health)。
    - 探测方法-`TCP SOCKET`: 尝试建立TCP连接(如检查端口是否监听)。
    - 探测方法-`EXEC`: 执行容器内命令，根据退出码判断(0表示成功)。
  - 每个Node上都有Kubelet，Kubelet会watch API Server，发现自己节点上有新的Pod，就开始真正的创建Pod。
  - Kubelet拉取Pod配置，Kubelet会拿到PodSpec
  - 管理Volume
  - 管理CNI

### 02-02-Kube-proxy: 负责节点的网络，在主机上维护网络规则并执行连接转发。它还负责对正在服务的pods进行负载均衡。
  - 监控集群中用户发布的服务，并完成负载均衡配置。
  - 每个节点的Kube-Proxy都会配置相同的负载均衡策略，使得整个集群的服务发现建立在分布式负载均衡器之上，服务调用无需经过额外的网络跳转(Network Hop)。

## 02-Kubectl命令和kubeconfig
  - kubectl是一个Kubernetes的命令行工具，它允许Kubernetes用户以命令行的方式与Kubernetes交互，其默认读取配置文件~/.kube/config。
  - Kubectl会将接收到的用户请求转化为rest调用以rest client的形式与apiserver通讯。
  - apiserver的地址，用户信息等配置在kubeconfig。
  - 常见命令:
    - kubectl get po -oyaml -w
      - `kubectl`: 可查看对象。
      - `-oyaml`: 数据详细信息为yaml格式。
      - `-w watch`: 该对象的后序变化。
      - `-owide`: 以详细列表的格式查看对象。
    - kubectl describe
    - kubectl exec
    - kubectl logs
      
## Kubernetes的所有管理能力构建在对象抽象的基础上，核心对象包括以下:

### Node: 计算节点的抽象，用来描述计算节点的资源抽象、健康状态等。
  - Node是Pod真正运行的主机，可以是物理机、也可以是宿主机。
  - 为了管理Pod，每个Node节点上至少要运行container runtime(比如Docker或者Rkt)、Kubelet和Kube-proxy

### Namespace: 资源隔离的基本单位，可以理解理解为文件系统中的目录结构。
  - Namespace是对一组资源和对象的抽象集合，比如可以用来将系统内部的对象划分为不同的项目组或用户组。
  - 常见的pods、services、replication Controllers和deployments等都属于某一个Namespace的(默认是default)，而Node、persistentVolumes等则不属于任何Namespace。

### Pod: 用来描述应用实例，包括镜像地址、资源需求等。Kubernetes中最核心的对象，也是打通应用和基础架构的秘密武器。
  - Pod是一组紧密关联的容器集合，它们共享PID、IPC、Network和UTS namespace，是Kubernetes调度的基本单位。
  - Pod的设计理念是支持多个容器在一个Pod中共享网络和文件系统，可以通过进程间通信和文件共享这种简单高效的方式组合完成服务。
  - 同一个Pod中的不同容器可共享资源:
    - 共享网络Namespace
    - 可通过挂载存储卷共享存储
    - 共享Security Context
  - 具备的特征:
    - 临时性: Pod是临时的, 随时可能被销毁重建
    - 独立IP: 每个Pod有独立Pod IP(集群内可路由)
    - 内含容器: 通常1个主容器 + 0-N个辅助容器(sidecar)
    - 不直接创建: 一般通过Deployment/Job等控制器创建
  - 生命周期:
    - Pending: 已创建, 等待调度: 可能资源不足、镜像拉取中
    - Running: 已调度且至少一个容器运行: 正常状态
    - Succeeded: 所有容器成功退出: Job/CronJob常见
    - Failed: 所有容器退出且至少一个失败: 需查询日志
    - Unknown: 无法获取状态: 通常节点失联

### Container: 
  - 生命周期:
    - Waiting: 容器还没跑起来, 比如正在拉取镜像、等待依赖
    - Running: 容器进程正在运行
    - Terminated: 容器已退出, 会带上exitCode和reason(比如: Completed、Error、OOMKilled)

### Deployment:
  - 是Kubernetes中用于申明和管理无状态应用的一种API资源对象.它用YAML描述“我想要应用长什么样子”,然后由Deloyment Controller持续工作, 让集群的实际状态与这个描述保持一致。
  - 三大核心能力
    - 副本控制: 维持指定数量的Pod副本
    - 滚动更新: 升级镜像时逐个替换, 零停机
    - 版本回退: 保留历史版本, 一键undo

### Service:服务如何将应用发布成服务，本质上是负载均衡和域名服务的声明。
  - Pod IP是动态的，调用方无法稳定访问。Service提供固定IP + 自动负载均衡
  - ClusterIP(默认): 集群内部，典型场景: 微服务之间调用
  - NodePort: 集群节点IP+端口(30000-32767)，典型场景: 临时对外、测试
  - LoadBalancer: 云厂商分配公网LB IP， 典型场景: 生产对外暴露
  - Ingress: 通过域名+路径路由到Service，典型场景: HTTP(s)对外(七层)
