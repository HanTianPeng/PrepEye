#### 一致性哈希算法
  - 普通的哈希: hash(key) % N
  - 一致性哈希: 哈希环: [0,100]-> A [100,300]->B [300,700]->C => 250->B 650->C 750->A; 新增节点[300,500]->D [500,700]->C
  - 一致性哈希解决了: 节点变化时，只影响局部数据，而不是全量洗牌。
  - 一致性哈希问题: 数据倾斜问题，随机哈希算法导致节点区间不均匀。解决这类问题通常采用虚拟节点来解决。
  - 虚拟节点: 将一个节点映射到多个虚拟节点上，用虚拟节点进行随机哈希算法，这样就可以保证节点区间相对均匀。

  - 节点之间gossip，传输网络包适合。
  - key -> slot -> node : 逻辑分片桶
  - 数据分布均匀
  - slot足够细 -> 平滑迁移
  - metaData维护成本

#### gossip(去中心化的信息传播协议)
  - PFAIL(主观下线): `cluster-node-timeout 15000`: 15s没有收到pong消息，则认为主观下线
  - FAIL(客观下线): 
  - `cluster bus`端口: client_port + 10000: 6379 + 10000 = 16379
  - 部分随机: PING选择的节点规则：长时间未通信的节点、PFAIL节点
  - MEET: 节点握手加入集群
  - PING: 主动探测，携带gossip；包含信息: 自己节点的信息node_id、epoch配置版本、slot信息、节点状态master/slave、gossip section其他节点的状态
  - PONG: 响应，携带gossip；包含信息: ack、gossip section其他节点的状态
  - FAIL: 广播某节点已客观下线
  - PUBLISH: pub/sub传播
  - FAILOVER_AUTH_REQUEST: 请求故障转移投票，计算failover delay(replication offset)
  - FAILOVER_AUTH_ACK: 投票确认

#### 如何避免无限重复选举
  - config epoch: 集群配置版本号，防止脑裂，全局递增；
  - slot ownership 冲突
  - failover后新的master合法性
  - 网络分区导致的脑裂

#### redis cluster: 去中心化分片系统
  - `多master + 多slave`集群: 分片(sharding) + 高可用(HA)
  - master: 持有slot、负责处理写请求、作为数据主分片
  - slave(replica): 复制master数据、master挂掉时接班、提供读扩展；只属于一个master；保证了高可用

#### redis cluster为什么不能multi-key跨槽
  - 跨槽意味着跨节点，而redis是单节点单线程原子执行
  - 去中心化 + 最终一致性，而不是强一致性分布式数据库；分布式需要2PC、分布式锁、rollback、Coordinator(协调者)
  - 利用hash tag解决

#### redis数据倾斜问题
  - 某些节点存的数据过多或则访问压力过大，导致这些节点成为瓶颈。
  - 容量倾斜: 
    - 大Key问题: 数据进行拆分
  - 访问倾斜: 
    - 本地缓存: 缺点: 多实例集群部署，导致数据不一致问题；
    - 单个Key问题: 热点Key打散(多副本随机读): 比如product:1,复制出product:1:01、product:1:02等
    - 读写分离: 主从延迟导致数据不一致问题；
    - 限流降级: 兜底策略
