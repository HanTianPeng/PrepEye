#### 1.惰性删除(Lazy Expire)
  - 核心指令执行单线程,几千万个定时器: 处理回调+上下文切换(cpu扛不住);导致没有空处理指令

#### 2.定期删除(Active Expire 隐性OOM问题: 冷数据堆积)
  - 主线程
    - 概率抽查机制(20个Key有25%过期)，避免全量扫描导致CPU暴涨。
    - 25ms止损防止阻塞
    - 主从延迟导致主从架构的"幽灵内存"

#### 双保底为什么还会出现OOM问题(内存淘汰策略的意义)
  - 写入速度大于删除速度
  - 大Key卡顿主线程

#### 3.内存淘汰策略(Eviction): 当Redis配置了maxmemory,并且实际内存达到上限后,再执行需要申请更多内存的写命令时,会触发内存淘汰策略
  - noeviction: Redis不会删除数据,而是直接返回`OOM command not allowed when memory > 'maxmemory'`
  - volatile-*: 只会从设置了过期时间的Key中淘汰数据
  - allkeys-*: 所有的Key中进行淘汰

  - 前提条件:
    - 配置了maxmemory
    - Redis内存达到上限后,如果再来一个写命令,需要申请更多内存,就会触发内存淘汰策略
    - 读操作一般不受影响,主要受影响的是新增数据、修改数据这类可能继续占用内存的命令
  
  - *参数配置细节:
    - LRU: 最近有没有被访问过; 最近最少使用的淘汰; 近似LRU + 随机采样
    - LFU: 访问频率高不高; 最不经常使用的淘汰; 近似LFU + 随机采样，避免了`历史热点污染`问题，利用了带时间衰减的概率频率统计，高16bit(上次衰减时间) + 低8bit(counter)
    - Random: 随机淘汰
    - TTL: volatile-ttl,只在设置了过期时间的Key中,优先淘汰剩余时间更短的Key
  
  - 配置策略:
    - 如果热点非常集中,且长期稳定;LFU更适合; 因为热点数据最近都被访问到,此时更应该关注的是频率;
    - 如果业务更关注:最近谁在被使用,LRU更适合;
    - Redis为了控制性能开销,采用的是近似LRU/LFU,而不是严格的全量排序;

#### 解决方案
  - 业务层: TTL加上随机时间戳防止大量Key集中过期
  - 配置层: 内存淘汰策略: 缓存(allkeys-lru)  数据库+缓存(volatile-lru)
  - 版本层: 大Key开启Lazy Free

##### LRU和LFU应该怎么选？
  - 如果业务热点变化快,更关注"最近谁在被访问",用LRU更直观;如果热点相对稳定,更希望保留长期高频数据,LFU往往更适合.

##### 为什么用了volatile-lru还是会 OOM？
  - 因为volatile-lru只能在带TTL的key中淘汰.如果很多key没有过期时间,Redis就找不到足够的候选数据,最终仍然可能报错.

##### noeviction模式下,读请求也会失败吗？
  - 一般不会.noeviction主要影响写入类命令,读请求通常还能继续执行.

##### Redis需要关注的状态
  - `used_memory`: 当前使用内存
  - `maxmemory`: 最大内存限制
  - `mem_fragmentation_ratio`: 碎片率
  - `maxmemory_policy`: 内存淘汰策略
