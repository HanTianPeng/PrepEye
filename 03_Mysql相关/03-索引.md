#### 01-B+树核心参数计算：
  - `InnoDB页大小默认16KB`。
  - 一个非叶子节点能存的索引条目: 假设一个bigint类型的主键占8字节，指针占6字节，一个索引条目共14字节；那么一个非叶子节点能存索引条目数：16KB ÷ 14字节 ≈ 1170个
  - 高度为2的B+树能存的数据量：叶子节点数 * 每页记录数。每个叶子节点同样16KB，假设从聚簇索引的B+树进行分析，一行数据1KB，每页16条。那么总数据量 = 1170 × 16 ≈ 18720条
  - 高度为3的B+树能存的数据量：总数据量 = 1170 × 1170 × 16 ≈ 2190万条。三次磁盘IO就能查到任意一条数据

#### 02-B+树、B树、红黑树、哈希表对比:
  - B树的非叶子节点也存数据，同样高度下能存的索引条目更少，树更高。而且B树叶子节点之间没有链表，范围查询需反复回溯父节点，性能差。
  - 红黑树是二叉树，2000万条数据高度约24层。内存中没有问题，但数据库数据在磁盘，24次磁盘IOVSB+树的3次，差距太大。
  - 哈希表只能做等值查询不能做范围查询。而且哈希冲突时性能不稳定。InnoDB的自适应哈希索引是给热点数据加的缓存，不是主索引。

#### 03-聚簇索引与辅助索引:
  - 聚簇索引：InnoDB表必须有一个聚簇索引。优先用主键，没有主键就用第一个非空唯一索引，都没有就自动生成一个6字节隐藏row_id。聚簇索引的叶子节点直接存储完整行数据。
  - 二级索引(辅助索引)：叶子节点存的是主键值，不是行地址。查询时先查主键，再到聚簇索引查完整数据。

#### 04-为什么存主键而非物理地址:
  - 因为页分裂会导致物理地址变化，如果存物理地址，地址变了所有二级索引都要更新，代价太大。存主键的话，主键值不变，只有聚簇索引需要维护数据位置。
  - 覆盖索引：如果查询的字段在二级索引里都有，就不需要回表。
  - MRR优化(Multi-Range Read)：当二级索引查到多个主键值，普通做法是逐个回表，随机IO。MRR先把主键值排序，再批量回表，将随机IO转顺序IO，性能提升明显。

#### 05-覆盖索引:
  - 查询所需字段全部在索引中，`MySQL`可以直接从`非聚簇索引`返回数据，不需要再`回表`查询`聚簇索引`。
  - 核心价值: 不回表、减少随机IO

#### 06-索引最左前缀原则:
  - B+树的索引是按照定义顺序排序的。先按a排序，a相同再按b排序，b相同再按c排序。所以查询必须从最左边开始，不能跳过。
  - `WHERE a = 1 AND b = 2 AND c = 3`:
  - `WHERE a = 1 AND c = 3`: 只能用a，c用不到。因为a相同后b不同，c是乱序的
  - `WHERE b = 2 AND c = 3`: 用不到任何索引，因为a没有指定，无法定位
  - `WHERE a = 1 AND b > 2 AND c = 3`: 只能用a和b。b是范围查询后，c是乱序的
  - `ORDER BY b, c WHERE a = 1`: 能用到a排序，b和c的排序也在索引里，不需要额外filesort

#### 07-索引下推(ICP: Index Condition Pushdown):
  - MySQL5.6引入: 比如查询a=1 and c=3，以前在存储引擎层只过滤a=1，返回给Server层再过滤c=3。索引下推在存储引擎层就过滤c=3，减少回表次数。
  - `ICP`的最优条件是先利用`非聚簇索引`进行`高效检索部分数据`，再利用剩余索引列在存储引擎层进一步过滤；减少回表次数。
  - 理解误区: 对于`非聚簇索引的全索引扫描`仍然可能会用到`索引下推`，

#### 08-最左前缀索引与覆盖索引冲突:
  - 使用了`最左前缀索引`就用不上`覆盖索引`对查询性能的优化
  - 使用前缀索引，定义好长度，关注索引的区分度，就可以做到既能节省空间，又不用额外增加太多的查询成本；`select count(distinct left(email, 4)) as l`

#### 09-范围查询的陷阱:
  - 联合索引中遇到范围查询`>、<、between、like 'xxx%'`，后面的字段就用不到了。但`in`不是范围，多个等值条件可以继续用。

#### 10-count的效率:
  - 推荐使用count(*): `count(*) ~ count(1) > count(主键ID) > count(字段)`

#### 11-exists与in的差别:
  - MySql5.6之前老版本:
    - IN: 先执行子查询生成集合；`select * from a where a.id in (select id in b)`；子查询表小更适合。
    - EXISTS: 相关子查询逐行判断；`select * from a where exists (select 1 from b where a.id=b.id)`；子查询表大更适合。
  - MySql5.6之后版本: 提供了多种优化策略 
    - `半连接优化(Semi Join)`
      - `select * from a where a.id in (select id in b)`可能优化器优化成`select distinct a.* from a join b on a.id=b.id`。
      - `LooseScan`: 跳跃扫描(SkipScan)的一种，利用索引跳过重复值；`select * from user where id in (select user_id from order)`，order中有索引user_id；
      - `FirstWatch`: exists的优化策略
      - `Duplicate Weedout`: 去重
      - 新版本取决于执行计划，可能两者之间没有差别。
    - `物化(Materialization)`

#### 12-三值逻辑:
  - TRUE/FALSE/UNKNOWN(缺失值而非特殊值)
  - `WHERE`语句只返回TRUE的数据
  - `select * from a where id not in (select id from b)`，b的id存在1,2,null三种情况，则这个sql返回空。
    - 原因`select * from a where id != 1 and id != 2 and id != null`，而id != null返回unknown，则整个where都返回unknown；所以结果为空。
  - `TRUE AND UNKNOWN`: UNKNOWN
  - `FALSE AND UNKNOWN`: FALSE
  - `TRUE OR UNKNOWN`: TRUE
  - `FALSE OR UNKNOWN`: UNKNOWN
  - `NULL = NULL`: UNKNOWN (sql认为两个未知数不一定相等)

#### 11-索引失效:
  - 根本原因: MySQL无法利用索引的有序性。索引是按照原始值排序的，对索引列做任何操作都会破坏这个顺序。

#### 12-索引失效场景及原理:
  - 条件字段函数操作: `WHERE DATE(create_time) = '2024-01-01'`，索引存的是时间，无法判断函数结果；对索引字段做函数操作，可能会破坏索引值的有序性，因此优化器就决定放弃走`树搜索功能`，但是不一定会放弃create_time索引的遍历。
  - 隐式类型转换: `WHERE phone = 13800000000`，phone是varchar，MySQL会把phone转换成数字，再和数字索引比较；如果`where id = "1000"`，id是int，MySQL默认将字符串转换成数字，所以没有影响。
  - 隐式字符编码转换: `utf8mb4`是`utf8`的`超集`；如果驱动表是`utf8mb4`，被驱动表是`utf8`，会导致连接过程中被驱动表的索引字段上有函数操作，从而被驱动表全表扫描。但相反则不会。
  - OR条件: `WHERE a = 1 OR b = 2`，两边都能用到索引，但合并成本高，可能全表扫描
  - 不等于: `WHERE a != 1`，不等于没法定位，只能扫全表
  - like '%xxx%': 前导通配符，不知道从哪开始查

#### 13-慢SQL排查流程:
  - 01-发现问题:
    - 开启慢查询日志，修改配置文件`my.conf`的相关配置项: `slow_query_log=on`，设置`long_query_time=20(单位是秒)`
    - 或则基于公司内部的慢查询监控平台就行查询
    - 首先考虑的优化方向: 1.合理的时间窗口  2. 查询时间 * 查询次数 = 执行总时长最长的SQL
    - 用`mysqldumpslow`分析慢查询日志
  - 02-定位问题:
    - `EXPLAIN`查询SQL执行计划
      - `Type`列:
        - `system`: 系统表，只有一行
        - `const`: 主键或唯一索引等值查询，最多一行
        - `eq_ref`: 联表查询，被驱动表用主键或唯一索引
        - `ref`: 普通索引等值查询
        - `range`: 范围查询
        - `index`: 全索引扫描
        - `ALL`: 全表扫描，性能最差
      - `Extra`列:
        - `Using Index`: 查询的条件全部在索引中，使用了`覆盖索引`，不需要回表操作。
        - `Using Index Condition`: 利用了`索引下推`优化，
        - `Using Where`: `Mysql`的`Server层`需要过滤数据；使用了索引但需要回表
        - `Using Where; Using Index`: 使用了`覆盖索引`，不需要回表操作；
        - `Using index for skip scan`: Mysql8.0版本之后，针对于低基数列作为联合索引的最左列(可枚举字段)，弱化索引的最左前缀原则，多次使用`range scan`利用`索引下推`优化减少回表次数。
        - `Using Temporary`:
        - `Using Filesort`:
      - `KEY`列:
        - 索引不符合预期，可通过`force index`强制使用某个索引。但MySQL的索引选择是基于统计信息的。今天好用的索引，数据分布变化后可能不好用。
        - 强制指定会导致未来性能问题。
        - 优先用`optimizer hints`或调整SQL结构，这个是MySql8.0版本之后的语法。
      - `ROWS`列:
        - `show index from t`: 查看表的各个索引的基数。
        - `show table status like t`: 主键索引是按照这个语句中`Rows`来估计的；其他非聚簇索引的基数需要考虑MVCC的历史版本问题。
        - 无论哪一种，都是采用采样统计的，原因是因为满足MVCC多版本并发控制后，无法和MyISAM一样，用一个统一且唯一的数字，用表记录下来。
  - 03-解决问题:
    - 优先进行`SQL`性能调优。
    - 针对于无法解决的慢SQL，进行架构升级，引入组件`ES`、`ClickHouse`、`Doris`等`NoSQL`数据库进行优化。
